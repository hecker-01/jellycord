# Skip the bot token, link users instead

A Discord bot token cannot set anyone's Rich Presence except the bot's own, and even on itself a bot gets only a plain "Watching <title>" line, with no poster, progress bar or buttons ([Discord Gateway docs](https://docs.discord.com/developers/events/gateway-events)). The original "supply a bot token and authorize it" plan therefore does not work. Two routes do. The first is a **local IPC companion**: a small desktop app writes `SET_ACTIVITY` to the user's running Discord client and needs only an Application ID. It is documented, stable, and used by nearly every existing Jellyfin presence tool, but it only works when the viewer has Discord running on a nearby PC. The second is **server-side presence through Discord's Social SDK "headless sessions"**: each Jellyfin user links their Discord account once via OAuth (scope `sdk.social_layer_presence`), and the server sets presence directly, with no desktop app anywhere. A working MIT-licensed Jellyfin plugin already does this over plain HTTP ([mrzeappleGit/jellyfin-plugin-discord-presence](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence)), but the endpoint does not appear in Discord's public docs. So "each person supplies their own token" becomes: **each Jellyfin admin creates one Discord application, and each viewer links their Discord account through OAuth**. My recommendation for jellycord is a 12.x (.NET 10) server plugin built around a pluggable "presence sink". The MVP uses the headless-sessions sink, after a one-day spike confirms the endpoint against your own Discord app. An IPC companion follows as the documented fallback, and bot output is optional extra. Two smaller decisions also need attention: Jellyfin 12 shipped in September 2026 and breaks all older plugins, and the name "jellycord" is already taken by a same-purpose repo.

## A bot token can set only the bot's own status

The Gateway "Update Presence" opcode (op 3) changes only the presence of the account that owns the connection. Discord also restricts bots to the activity fields `name`, `state`, `type` and `url`, so a bot cannot show images or timestamps even on its own profile ([Gateway Events docs](https://docs.discord.com/developers/events/gateway-events)). The OAuth scope built for this job, `activities.write` ("allows your app to update a user's activity"), is marked **"not currently available for apps"**. The RPC scopes `rpc` and `rpc.activities.write` are reserved for approved partners ([OAuth2 docs](https://docs.discord.com/developers/topics/oauth2)). The only other way to drive a user's account from a server is to send op 3 with the user's own token. That is self-botting, which Discord says is "forbidden, and can result in an account termination" ([Discord Support](https://support.discord.com/hc/articles/115002192352)), so jellycord must never ask users for their Discord token.

That leaves three mechanisms that actually work, each with a different trade-off.

| Mechanism | Sets the user's own presence? | Where Discord must run | Credentials | Documented? |
|---|---|---|---|---|
| Bot status / channel embeds | No: bot status (name/state only) or messages in a channel | Nowhere | Bot token | Yes |
| Local IPC `SET_ACTIVITY` (companion) | Yes: Watching type, poster, progress bar, buttons | Same PC as the companion (desktop; Android via SDK 1.10+) | Application ID only | Yes ([RPC docs](https://docs.discord.com/developers/topics/rpc)) |
| Social SDK authenticated presence (headless) | Yes | Nowhere | Per-user OAuth token, scopes `openid sdk.social_layer_presence` | SDK yes; HTTP endpoint no |

The IPC path is well understood. A client connects to the `discord-ipc-{n}` pipe (Windows `\\?\pipe\discord-ipc-{n}`, and on Unix under `XDG_RUNTIME_DIR` or `/tmp`), handshakes with the `client_id`, and sends `SET_ACTIVITY` with details, state, timestamps and assets ([RPC docs](https://docs.discord.com/developers/topics/rpc)). Discord added the **Watching type to RPC on July 25, 2024**, and **`status_display_type` plus clickable `details_url`/`large_url` fields on July 17, 2025** ([Change Log](https://docs.discord.com/developers/change-log)). The RPC page still warns that unapproved apps need tester access. In practice that warning covers the authenticated RPC commands and the deprecated WebSocket transport, not client-ID-only IPC presence, which the Social SDK docs describe as the "unauthenticated" mode and which requires that "the Discord desktop client must be running on the user's machine" ([Setting Rich Presence](https://docs.discord.com/developers/discord-social-sdk/development-guides/setting-rich-presence)). The large community of working tools confirms this reading. The weakness is equally clear: your viewers watch on TVs, phones and browsers, and none of those run Discord's desktop client on the device doing the watching.

The Social SDK's authenticated mode avoids that requirement. The user links their account through OAuth with `openid sdk.social_layer_presence` (what `Client::GetDefaultPresenceScopes` returns), and an SDK client holding that token sets presence for them ([Setting Rich Presence](https://docs.discord.com/developers/discord-social-sdk/development-guides/setting-rich-presence); [Social SDK OAuth2 Scopes](https://docs.discord.com/developers/discord-social-sdk/core-concepts/oauth2-scopes)). Presence is not behind an approval. Only chat, voice and lobbies require the "Comms Access" review ([Communication Features](https://docs.discord.com/developers/discord-social-sdk/core-concepts/communication-features)). The community daemon easy-presence already runs this headless on Linux, holding "one Discord connection per linked user" at about 4–5 MB each ([easy-presence](https://github.com/LunathDePixel/easy-presence)). The catch is the official SDK itself: it is closed-source native C++, cannot be redistributed, and is limited to x86-64 Linux with desktop audio and X11 libraries ([music-assistant discussion #2041](https://github.com/orgs/music-assistant/discussions/2041)). That makes it a poor fit for loading inside a .NET plugin running in Docker or on a Raspberry Pi.

## The headless-sessions endpoint is real but undocumented

The research notes disagree. A search of Discord's official documentation found **no trace of a "headless-sessions" endpoint**. Discord's own "Use with Discord APIs" page lists only token exchange, `/users/@me` and lobby creation as HTTP examples, and names no presence endpoint ([Use with Discord APIs](https://docs.discord.com/developers/discord-social-sdk/how-to/use-with-discord-apis)). The prior-art review, by contrast, read source code that calls `POST https://discord.com/api/v10/users/@me/headless-sessions` with a per-user OAuth token carrying `sdk.social_layer_presence` ([DiscordApi.cs](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence/blob/main/Jellyfin.Plugin.DiscordPresence/DiscordApi.cs)).

The two findings do not actually contradict each other. They describe the same thing from two angles: a real endpoint that Discord does not document publicly. Three pieces of evidence support that conclusion. First, the mrzeappleGit code contains operational detail that someone would only know by running it against Discord: sessions **expire at 20 minutes and are refreshed every 14**, the session token **"rotates on every response"**, and users can link through a device code at `discord.com/activate` ([README](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence); [PresenceService.cs](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence/blob/main/Jellyfin.Plugin.DiscordPresence/PresenceService.cs)). Second, Discord's changelog says Social SDK 1.1 (April 16, 2025) added "sending rich presence updates and invites **without connecting to the Discord gateway** on desktop" ([Change Log](https://docs.discord.com/developers/change-log)). Presence without a gateway connection has to travel over some HTTP endpoint, and the closed-source SDK almost certainly calls one like this. Third, the scope it uses is the documented, self-serve Social SDK presence scope, not a partner-only scope.

My confidence is **moderate-to-high (about 75%) that the endpoint exists and works today** for any application with the Social SDK enabled, and **low that it is a stable contract**. The repo has zero stars and a single author. Discord documents nothing about the endpoint's schema, rate limits or lifetime. The Social SDK Terms reserve Discord's right to "change, suspend, limit the availability of, or discontinue" the SDK ([Social SDK Terms](https://support-dev.discord.com/hc/en-us/articles/30225844245271-Discord-Social-SDK-Terms)). The plugin's own author flags two caveats. There is "no presence-only scope", because `sdk.social_layer_presence` "also grants reading and writing the user's Discord friends list". And because the SDK is framed around games, "if Discord ever gates it differently, statuses may stop" ([README](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence)). Two further gaps remain open: whether Discord's terms allow a non-game media app to use the Social SDK (the terms page could not be fetched directly), and how a headless presence merges with a presence the user's desktop client is already showing. Treat headless sessions as the best user experience available, but build so you can switch to another delivery method without a rewrite.

This also clarifies the "own token/app" model. An open-source plugin cannot ship a shared client secret, so **each Jellyfin admin registers one Discord application**, enables the Social SDK in the Developer Portal, and pastes the client ID and secret into jellycord's config. Each viewer then links their own Discord account once. Viewers never need a developer app of their own ([Discord blog](https://discord.com/blog/discords-powerful-cross-platform-chat-ready-for-your-game)). Device-code linking matters for LAN-only servers, because it does not require Discord to reach a redirect URL on your server.

## Target Jellyfin 12 first, and treat 10.11 as optional

Jellyfin dropped the "10." prefix and **shipped 12.0 on September 8, 2026**, with 12.2 following on October 5. 12.x targets **.NET 10**, and the release notes say plainly that "plugins have to be retargeted and rebuilt" ([v12.0 release](https://github.com/jellyfin/jellyfin/releases/tag/v12.0); [Jellyfin releases](https://github.com/jellyfin/jellyfin/releases)). The mapping is one server line to one runtime: 10.11 uses net9.0 with `Jellyfin.Controller`/`Jellyfin.Model` 10.11.x (last 10.11.11), and 12.x uses net10.0 with 12.0.0–12.2.0 ([NuGet Jellyfin.Controller](https://www.nuget.org/packages/Jellyfin.Controller/)). Reference those packages with `ExcludeAssets=runtime`. A version mismatch makes the plugin show as NotSupported ([plugin template](https://github.com/jellyfin/jellyfin-plugin-template)). `targetAbi` behaves as a minimum server version: a 10.10.7 server does not see a build with targetAbi 10.11.0.0 ([tvheadend #106](https://github.com/jellyfin/jellyfin-plugin-tvheadend/issues/106)). The official template is still on net9.0/10.11.5 and has no 12.x update ([template csproj](https://raw.githubusercontent.com/jellyfin/jellyfin-plugin-template/master/Jellyfin.Plugin.Template/Jellyfin.Plugin.Template.csproj)), so you will retarget it yourself.

Supporting 10.11 later costs relatively little, because jellycord touches only `ISessionManager`, `IUserManager` and `BaseItem`. The one relevant 12.0 API break is `IUserManager.Users` becoming `GetUsers()` ([v12.0 release](https://github.com/jellyfin/jellyfin/releases/tag/v12.0)). That break can be handled with `#if` and multi-targeting `net9.0;net10.0`, publishing two zips with different targetAbi values in one manifest, as Posterizarr does ([posterizarr 3.3.2](https://newreleases.io/project/github/fscorrupt/posterizarr/release/3.3.2)). Watch out for ABI drift inside a single line: plugins built against the 10.11.0 packages threw `MissingMethodException` on 10.11.9 because a session or user member changed its return type ([Jellyscribe v1.13.0](https://newreleases.io/project/github/builtbyproxy/Jellyscribe/release/v1.13.0)). If you do ship a 10.11 build, set its floor at 10.11.9.0.

On structure, `IServerEntryPoint` is gone. Register a hosted service through `IPluginServiceRegistrator.RegisterServices(IServiceCollection, IServerApplicationHost)` ([IPluginServiceRegistrator.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Plugins/IPluginServiceRegistrator.cs)), and keep it separate from the plugin class, which "cannot also be a IHostedService" ([template README](https://github.com/jellyfin/jellyfin-plugin-template)). Add REST endpoints with an `[ApiController]` that derives from `ControllerBase`, protected by `[Authorize]` or `Policies.RequiresElevation` ([Policies.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Common/Api/Policies.cs)). Distribute through your own `manifest.json` on GitHub Pages, with MD5 checksums and zips on GitHub Releases ([official manifest example](https://ams1.mirror.jellyfin.org/files/plugin/manifest.json)).

## Playback events need debouncing before they reach Discord

`ISessionManager` raises `PlaybackStart`, `PlaybackProgress` and `PlaybackStopped`, plus `SessionEnded` ([ISessionManager.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Session/ISessionManager.cs)). The event args carry `Users`, `Item`, `PlaybackPositionTicks`, `IsPaused`, `IsAutomated`, `PlaySessionId` and `Session` ([PlaybackProgressEventArgs.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Library/PlaybackProgressEventArgs.cs)). Three server behaviours shape the design. First, **progress events fire on every client report, with no throttling**. Second, the server generates its own **automated ticks** (`IsAutomated == true`) after each real report. Third, a client that dies without reporting a stop is cleaned up only by a **5-minute idle check**, so "now playing" can stay stale for 5–10 minutes ([SessionManager.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/Emby.Server.Implementations/Session/SessionManager.cs)). Discord, meanwhile, allows only **5 presence updates per 20 seconds** on a gateway connection ([Gateway Events docs](https://docs.discord.com/developers/events/gateway-events)), and headless sessions have their own undocumented limits.

Use a singleton hosted service that subscribes to these C# events, keyed by `PlaySessionId` and the Jellyfin user ID. It should do only cheap work inside the handlers and push state changes into a `Channel<T>` that a background worker drains. The worker should send to Discord on start, on item change, on a pause/resume transition, and on a seek, which it detects when the reported position deviates from wall-clock elapsed time by more than about 10 seconds. kennethsible uses that 10-second `SEEK_THRESHOLD`, and mrzeappleGit turns off seek detection while paused because otherwise "every pause looks like a seek" ([kennethsible/jellyfin-rpc](https://github.com/kennethsible/jellyfin-rpc); [PresenceService.cs](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence/blob/main/Jellyfin.Plugin.DiscordPresence/PresenceService.cs)). Ignore automated ticks when detecting pauses and seeks. Debounce clears by about 2 seconds so autoplaying the next episode does not flicker, as kennethsible's `SESSION_TIMEOUT` does. Skip theme media, which both the webhook plugin and jellyfin-rpc filter out ([Webhook PlaybackProgressNotifier.cs](https://github.com/jellyfin/jellyfin-plugin-webhook/blob/master/Jellyfin.Plugin.Webhook/Notifiers/PlaybackProgressNotifier.cs); [jellyfin-rpc lib.rs](https://github.com/JustRadical/jellyfin-rpc/blob/main/jellyfin-rpc/src/lib.rs)).

Map the presence the way prior art has settled on. Use type 3 (Watching) for video and 2 (Listening) for audio. Set `status_display_type` to Details so the member list shows the title rather than "Jellyfin". For an episode, use the series name as `details` and "S2E5 · Episode title" as `state`. Send start and end timestamps while playing, which is what produces Discord's progress bar for Watching and Listening activities ([Gateway Events docs](https://docs.discord.com/developers/events/gateway-events)). While paused, drop the timestamps, append "(paused)", and optionally clear after a timeout. Add up to two buttons (IMDb/TMDB from `ProviderIds`, skipping localhost URLs), and tell users that buttons are **visible only to other people** ([exy README](https://github.com/xyxxyxxy/exy)). Pad `details` and `state` to at least 3 characters and truncate them at 128 ([jellyfin-rpc lib.rs](https://github.com/JustRadical/jellyfin-rpc/blob/main/jellyfin-rpc/src/lib.rs)).

## LAN-only servers need an image fallback chain

Discord accepts any publicly reachable HTTPS URL in `large_image` and proxies it through `mp:` media-proxy references ([Gateway Events docs](https://docs.discord.com/developers/events/gateway-events)). The field is limited to **300 characters** ([ActivityAssets reference](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1ActivityAssets.html)). Jellyfin makes the easy case very easy: `GET Items/{id}/Images/Primary` **has no `[Authorize]` attribute** ([ImageController.cs](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/ImageController.cs)), so a public server can pass `{PublicUrl}/Items/{seriesId}/Images/Primary?fillHeight=512&quality=90` with no token. Never append `api_key`, because the URL is visible to everyone who looks at the profile. A LAN-only server, however, is invisible to Discord's proxy. Radiicall's FAQ says it directly: "your server needs to be port forwarded for images to work" ([jellyfin-rpc FAQ](https://github.com/JustRadical/jellyfin-rpc/wiki/Frequently-Asked-Questions)).

Build the resolver as an ordered chain, as the more mature tools do. Step one: if the admin configured a public URL, use the direct Jellyfin image. Step two: look up a public poster from the item's provider IDs. TMDB needs an API key plus a call to get `poster_path`, and the Cover Art Archive covers music without a key ([kennethsible/jellyfin-rpc](https://github.com/kennethsible/jellyfin-rpc)). Pankyop's plugin also falls back to AniList, TVMaze and Wikipedia with a 3-second timeout ([ArtworkResolver.cs](https://github.com/Pankyop/rich-presence-for-jellyfin-in-discord-Plugin/blob/main/Jellyfin.Plugin.DiscordRichPresence/Discord/ArtworkResolver.cs)). Step three, which the admin must opt into: upload the poster to a temporary host. Litterbox with a 72-hour expiry and a per-item URL cache is what both Radiicall and the Plex reference tool DRPP use ([litterbox.rs](https://github.com/JustRadical/jellyfin-rpc/blob/main/jellyfin-rpc/src/external/litterbox.rs); [DRPP](https://github.com/phin05/discord-rich-presence-plex)). Step four: a static Jellyfin logo. Upload posters to a third party only with explicit consent, because doing so publishes the server's artwork. For episodes, prefer the series poster, and square the image before upload, because Discord crops the large image to a square.

## Small 2026 plugins are the only prior art, and the name is taken

Most Jellyfin presence tools are desktop clients that poll `/Sessions` and write to IPC. The best known, Radiicall/JustRadical's **jellyfin-rpc (Rust, GPL-3.0, 541 stars) is now archived** ([repo](https://github.com/JustRadical/jellyfin-rpc)). The most active successor is **kennethsible/jellyfin-rpc (Python, MIT)**, which has TMDB and Cover Art Archive fallbacks and uses Jellyfin's WebSocket when one is available ([repo](https://github.com/kennethsible/jellyfin-rpc)). Server plugins are new and small, and each takes a different approach. Phew's .NET 8 plugin exposes `/Plugins/DiscordRpc/Presence/Me` for a Python CLI to poll, and has no license ([Phew/jellyfin-rpc](https://github.com/Phew/jellyfin-rpc)). Pankyop's MIT plugin writes to the IPC pipe on the server host, which only helps when Jellyfin runs on the same desktop as Discord ([Pankyop](https://github.com/Pankyop/rich-presence-for-jellyfin-in-discord-Plugin)). mrzeappleGit's MIT plugin uses headless sessions ([mrzeappleGit](https://github.com/mrzeappleGit/jellyfin-plugin-discord-presence)). All three have zero stars. No project yet pushes presence from a server plugin to a desktop companion over SSE or WebSocket, so that part of the design is open. Licensing works in your favour: a Jellyfin plugin links against GPL assemblies, and the MIT code from mrzeappleGit (the headless client) and kennethsible (artwork lookups) can be reused with attribution. DRPP is AGPL-3.0, so use it for its design (WebSocket subscription, image-host abstraction, templated fields), not its code.

"Jellycord" is a crowded name. **yhqe/jellycord** is literally "discord rich presence for jellyfin", published under the package name `jellycord`. It is dormant, with no README and no stars ([repo](https://github.com/yhqe/jellycord)). At least six other repos use the name, including SiddheshDongare/Jellycord, a JFA-GO invite bot that is also on Docker Hub as `sidikulous/jellycord`, and Vernoxvernax/JellyCord, a library-announcement bot ([GitHub search](https://github.com/search?q=jellycord&type=repositories); [Docker Hub](https://hub.docker.com/r/sidikulous/jellycord)). Nothing technical stops you, because Jellyfin identifies plugins by GUID. But search, issue reports and Docker tags will get mixed up. Either publish as "Jellycord Presence" with the assembly `Jellyfin.Plugin.JellycordPresence`, or pick a distinct name before the first public release, while renaming is still free.

## Recommended architecture and phased plan

Structure jellycord as one 12.x plugin with four parts. A **PlaybackListener** (hosted service) turns session events into a normalized `PresenceState` per user. A **PresenceMapper** turns that state into a Discord activity: type, details, state, timestamps, buttons and `status_display_type`. An **ArtworkResolver** runs the fallback chain above and caches results. A set of interchangeable **IPresenceSink** implementations deliver the activity. The sinks are `HeadlessSessionSink` (per-user OAuth, server-side), `CompanionSink` (an authenticated SSE/long-poll endpoint for a desktop IPC companion), and an optional `BotSink` (channel embeds, or "Watching" on the bot itself for single-user servers). Configuration splits along the same lines. The admin page holds the Discord application credentials, the public URL, the image policy and the allowed libraries. A user-facing link page under `[Authorize]` lets each viewer connect Discord, choose a sink, and opt out of specific libraries. Store OAuth refresh tokens outside the XML plugin config, in a 0600 file under the plugin data directory as mrzeappleGit does, so they are never echoed back through `getPluginConfiguration`.

If not, swap phases 1 and 2. |

## Conclusion

The question that matters is not how to get a token. It is where the Discord session lives. A bot token keeps the session on Discord's side but under the bot's identity. IPC keeps it on the viewer's desk. Headless sessions are the only option that puts it on your server under the viewer's identity, which is what a TV-and-phone household needs, and they rely on an endpoint Discord has never promised to keep. That asymmetry is why the sink abstraction matters more than any single integration. Build the playback and mapping core once and ship headless first. Keep the documented IPC companion ready as the fallback, so that if Discord changes the rules, jellycord needs a new sink rather than a rewrite.

The open risks, in order of severity. Discord could gate or remove headless sessions, or rule that non-game media apps may not use the Social SDK. Users may balk at a scope that also grants friends-list access, so state it on the link page. Discord's undocumented headless rate limits and session merging could cause flicker or override what the user's desktop client is showing. Jellyfin 12.x point releases could repeat the 10.11.9 ABI break, so pin and test each minor version. LAN-only installs will show only a logo unless the admin opts into a third-party image host. And the name collision gets harder to fix with every user you gain.
